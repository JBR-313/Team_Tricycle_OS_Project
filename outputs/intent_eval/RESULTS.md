# Natural-language intent → scheduler config — the LLM's actual lane

Generated by `experiments/intent_eval.py` (advisor: `tools/intent_advisor.py`,
Solar Pro 3). The LLM reads ONLY an operator's English description of a workload
and emits a scheduling config; we grade its pick against a standard OS rubric it
never sees, and check the Algorithm Guard accepts it.

## Why this is the right test for the LLM
Our measured negatives (algorithm pick, mid-run switch, numeric burst prediction —
`outputs/random_eval/RESULTS.md`, `outputs/adaptive/RESULTS.md`) show the LLM does
NOT beat classical methods in the quantitative hot path. But those tests stripped
the semantic channel to be fair to numeric baselines. Here we test the LLM where
it has **no classical competitor**: translating free-form human intent into a
valid scheduling configuration. No heuristic reads English.

## Result (8 intents, Solar Pro 3, temp=0)

| metric | score |
|---|---|
| intent → OS-acceptable algorithm family | **8 / 8 (100%)** |
| Algorithm-Guard-valid config             | **8 / 8 (100%)** |

Every pick was both defensible and guard-valid, and the implied `target_metric`
was correct too — e.g. "responsiveness above all" → RR / avg_response_time;
"overnight batch, maximize throughput" → FCFS / throughput; "short jobs should
preempt longer ones" → SRTF; "strict importance, no starvation" → PRIORITY.

## End-to-end demo (real kernel)
`python3 scripts/orchestrator.py --intent "Interactive desktop session; users
expect instant response, latency matters most." --workload interactive`
→ intent → **RR** (avg_response_time) → guard ✓ → all six algorithms run on xv6 →
**judgment=SUCCESS, regret=0.0** (RR was the measured-best here) → natural-language
trace explanation. "Describe your workload in English; xv6 runs the right
scheduler and explains why."

## Honest framing
This does NOT claim the LLM picks the metric-optimal algorithm in general (often it
cannot on xv6 — measured, info-bounded). It claims the LLM correctly TRANSLATES
human intent into a sensible, valid, runnable configuration and explains the
result — the part of "LLM for OS" with no classical substitute.

## The project's two-sided, honest conclusion
- **LLM out of the hot path:** as the quantitative decision-maker (which algorithm,
  when to switch, how long the next burst) it loses to cheap classical methods.
- **LLM at the human interface:** intent → config and trace → explanation, it
  succeeds (8/8) — because those tasks have no heuristic alternative.

That boundary, measured on a real deterministic kernel with negative controls, is
the project's contribution: *put the LLM at the OS's human-facing layer, not in
its decision hot path.*
